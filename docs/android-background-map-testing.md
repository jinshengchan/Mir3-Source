# 安卓后台与换图优化测试

仅在 `codex/resource-fixes-testing-20261007` 测试分支验证，暂不合并 main。服务端协议、连接地址和资源包校验规则沿用当前测试版本。

资源按本次要求使用最早提供的原版 APK（云盘文件 ID `1Fts3QP26o2YbJ08Pb99GNv6QiHv86D8S`）内的旧资源：156 个资源文件，包括基础包及 152 个补丁。基础包 MD5 为 `ea9cba07c8e11cc5b9892b3bdaf30bb9`，沿用它原有的资源清单进行校验。

## 改动

- 安卓游戏连接在 Socket 收包回调中直接回应原有 `Ping`，不依赖游戏帧循环。其他数据包继续排队，回到前台后由游戏线程按顺序处理。
- 切后台后保活窗口为 3 分钟，CPU 锁到期自动释放，回前台立即释放。不会启动常驻通知服务。达到时限或积压 4096 个数据包后停止保活，避免积压大量游戏状态；此时需要重新登录。系统杀进程、限制网络或服务器主动断开仍会结束连接。
- 安卓普通发送和心跳发送共用串行发送队列，处理未一次发送完的缓冲区，避免切前后台时数据交错。
- 换图不再清空所有纹理或强制执行 GC。保留原有 3 分钟素材缓存淘汰，以及换图和人物坐标变化时的地图层刷新。随机传送可复用已加载的素材；首次到达未加载区域仍可能需要读取、解码或下载。
- 地图合成改为轮流使用两张绘制纹理。同尺寸刷新复用它们，尺寸或缩放变化时才重新分配，销毁控件时一起释放。
- 可见地面已经准备好、帧耗时不超过 33 ms 时，预热绘制范围外的 4 格地面和建筑；每帧最多尝试 6 个图片，2 ms 后不再启动下一次准备，待处理清单最多 512 个。一次文件读取、解码或 GPU 上传不能中途暂停，因此 2 ms 是启动工作的预算，不是硬性帧耗时保证。优先处理当前画面，换地图或移动 2 格后清掉旧的预热清单。
- 微端返回的 `Data/Map Data` 图片在已有后台任务中完成 Deflate 和 DXT 解码，游戏线程只上传已解码像素；其他素材沿用原流程。解码检查主体、阴影和叠加层的长度及像素尺寸，不改变图片、资源版本或下载校验。
- 首次读取本地 `Data/Map Data` 图片也交给两个 CPU 工作线程解码，GPU 创建、上传和可见像素初始化仍在游戏线程。最多保留 32 个正在准备或等待上传的本地图图片、预估像素总量不超过 32 MiB。未消费结果 5 秒后可淘汰；换地图或单帧跳跃超过 3 格时取消旧位置准备任务，取消中的工作仍计入限额直到完成。单张图片超过预算时沿用原同步路径。
- 素材请求并行上限由 10 调整为 24，用于测试首次进入新区域时分批请求的等待；资源头请求也使用原子方式占用配额。保留超时、重试、资源头及索引校验。实际收益依赖微端响应速度，需要手机测试，不把提高上限当作已证明的网络提速。
- 普通地图图片及混合地图图片在读取像素之前，使用已有索引中的尺寸、绘制偏移、缩放和当前绘制目标大小检查是否进入画面。完全不可见的图片不发请求、不解码、不上传，也不标记当前画面未完成；保留原有额外 25 行建筑扫描，高建筑从屏幕外延伸进画面时仍绘制。四像素纹理补齐及一像素边缘余量避免边界误裁。仅应用于 `Data/Map Data` 的整张图片与单位矩阵绘制，界面、人物、阴影变换、裁剪源矩形沿用原路径。
- 周边预热等待当前地面和可见对象均准备好，避免与尚未出现的建筑、人物抢占准备配额。显示仍逐帧更新，不保留旧场景等待目的地图片。

这些改动减少绘制纹理分配和临时加载；不会在人物移动时保留旧地图截图。随机传送目的地在服务器回复之前未知，首次抵达未准备的区域仍可能渐进显示，不能仅凭编译通过承诺所有换图都达到 PC 的效果。

没有绕过资源完整性校验，也不能靠缓存补齐缺失、损坏或版本不匹配的素材。

## 验证

`tests/BackgroundConnection.Tests` 链接实际 `BaseConnection`、`Packet`、`GeneralPackets` 和 `Time` 源码，以本机真实 TCP 验证：

1. 游戏帧处理暂停时仍回应心跳，恢复后游戏数据按序在恢复线程处理。
2. 切后台前收到的心跳不会留在已暂停的游戏队列中。
3. 到期停止保活，及时恢复可清除时限，Socket 回调不调用界面断开方法。
4. 后台队列达到上限后停止继续接收。
5. 大数据发送、心跳与帧发送并发时保持数据顺序和完整性，暂停后完成排队的心跳回复。

CI 同时运行现有资源安装、动画、资源头恢复检查，并检查仓库协议、APK 资源完整性与签名。实际手机上的系统后台行为和 GPU 画面需按下面步骤测试。

`tests/MapLoading.Tests` 链接实际地图像素解码器、DXT 解码器、预热队列和本地 CPU 准备队列，验证两种资源格式的 DXT1/3/5、三层偏移、RGBA、无效图片拒绝，以及预热去重、重试、数量和时间预算。另检查准备队列的 32 项和 32 MiB 上限、取消和过期结果释放、异常交回游戏线程。

## 手机测试

1. 正常登录后切后台 30 秒、1 分钟、接近 3 分钟，分别回到前台观察能否继续操作。超过 3 分钟后检查能否正常重新登录。先在较安静的地图测试，再在多人场景测试。
2. 在同一地图连续随机传送，再往返同一组地图。对比第一次和后续访问时黑块持续时间、人物动画和卡顿。
3. 在已出现黑块的位置停留，判断是否能补齐；持续不补齐的情况收集 `connection-debug.txt`，继续核对对应素材。
4. 留意多次换图后的内存、闪退，以及长时间后台或熄屏后的连接状态。这里没有承诺 Android 系统一定保留后台进程。
5. 对比走向新区域、反复传送到已访问区域和第一次传送到远处的加载时间。`connection-debug.txt` 的 `map-cache` 行包含 `renderMs`（地图合成 CPU 提交耗时，不含完整 GPU 执行）、`renderTargets`（地图绘制纹理累计分配数，首次同尺寸刷新通常为 2，后续同尺寸不应持续增加）、`preloadPending`（待预热图片数）、`localDecodePending`（本地准备任务）、`microActive`（正在请求的图片）、`microCompleted`（累计完成的图片请求）和 `microTotalMs`（累计请求耗时，包含失败请求及客户端处理）。`mapBoundsChecks` 与 `mapOutsideView` 分别计累计检查与跳过的地图图片绘制次数，不是独立图片数或下载数。地图统计有独立的 600 条预算，不再被 5000 条数据包日志挤掉。
6. 用相同地图和缩放测试四个边缘、屏幕外延伸进来的高建筑、移动和随机传送，检查裁剪没有新增缺图。单元测试覆盖尺寸、正负偏移、缩放、纹理补齐和屏幕外建筑，并比较额外 25 行扫描的矩形覆盖；这不能代替手机 GPU 画面测试。
