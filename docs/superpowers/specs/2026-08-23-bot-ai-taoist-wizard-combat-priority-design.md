# 假人道士与法师战斗技能顺序设计

## 目标

修复两个已确认的战斗行为：

- 道士给怪物施毒后，攻击符或近战技能未被选中，直接退化为普通攻击。
- 法师始终按单体场景选择技能，即使周围已有三只或更多可攻击怪物，也不会选择群攻技能。

本次只调整服务端假人的道士、法师战斗选择和近身施法回退。技能学习、补给、喝药、地图、经济、其他职业及客户端逻辑保持不变。

## 已确认方案

采用按周围怪物数量动态选择的最小方案。群攻阈值统一为三只可攻击怪物；不足三只时使用单体技能，达到三只时允许群攻参与伤害评估。不会固定轮放某个群攻技能，也不会无视冷却、魔法值、装备和技能是否已学习。

未采用以下方案：

- 两只怪就强制群攻：更耗蓝，且会改变当前三只怪群攻阈值的既有约定。
- 固定群攻技能表轮放：会绕过现有伤害、冷却和蓝耗评估。
- 把整套战斗执行迁移到 Python：超出本次故障修复范围，且会扩大运行风险。

## 道士顺序

道士现有召唤、治疗和 Buff 模块继续先于战斗输出执行。进入怪物输出后按以下顺序：

1. 给目标补缺失的红毒和绿毒；三只以上时允许已学会且可用的群体施毒。
2. 选择可用攻击符。少于三只时过滤群攻符；三只以上时让群攻符和单体符共同参与预计总伤害及蓝耗评估。
3. 如果攻击符不可用，选择道士近战技能。单体优先可用的空拳刀法；三只以上允许横扫千军参与选择。
4. 上述技能均不可用时才普通攻击。

攻击符仍必须满足已学习、冷却完成、魔法值足够及护身符可用等现有条件。失败时沿既有回退链继续，不新增无限重试。

## 法师顺序

法师每次进入输出决策时，以自身位置为中心统计半径二格内可攻击怪物：

1. 少于三只时，只从现有单体候选中选择技能。
2. 三只以上时，将现有已定义的群攻与单体候选共同交给伤害评估；群攻按单次预计伤害乘附近怪物数量计算总收益。
3. 最优群攻不可用时继续选择可用单体技能；所有法术都不可用时才进入现有普通攻击回退。

法师现有元素抗性自适应继续保留。单体场景仍过滤群攻；群体场景不再强制过滤群攻。

## 近身施法

法师或道士距离目标小于偏好距离时，仍先尝试拉开距离。如果没有可走位置，但已选技能本身有效且目标仍在技能允许距离内，则原地施放，不因走位失败直接退化为普通攻击。

刺客的远程处理不改变；战士及其他职业逻辑不经过这条远程选择链。

## 接口与最小改动范围

计划只修改：

- `Server/BotSkillSelector.cs`
  - 让法师远程技能选择接收真实附近怪物数量。
  - 让道士攻击符选择接收真实附近怪物数量。
  - 接入已有但未使用的道士近战技能优先级。
- `Server/BotManager.Combat.cs`
  - 为法师计算附近怪物数量并传给选择器。
  - 保证道士攻击符失败后先尝试近战技能，再普通攻击。
  - 允许法师和道士在拉开距离失败但施法距离合法时原地施法。
- `.diagnostics/bot-ai-taoist-wizard-combat-priority-contract.ps1`
  - 新增本次行为的聚焦静态契约。

不修改数据库、客户端、补给购买、自动学习阈值、Python 策略设计、部署目录或其他诊断文件。

## 验证标准

严格按 RED、GREEN 顺序：

1. 先新增聚焦契约并运行，必须因当前代码仍硬编码法师单体场景、道士未接入近战回退等目标原因失败。
2. 再进行最小生产修改，重复运行聚焦契约并通过。
3. 重跑现有道士自动技能、道士补给、阶段一、40级/刺客、CPU/喝药和刺客走位契约，确保无回归。
4. 使用 Debug / AnyCPU 在隔离输出目录重建服务端，要求零编译错误；不覆盖用户当前运行的旧版 `Server.exe`，不部署、不启动、不停止服务。

静态契约和编译不能代替游戏内验证。最终仍需手工观察：三只以上怪物时法师实际施放群攻，道士补毒后使用攻击符，攻击符不可用时使用近战技能，以及近身无路可退时仍能施放合法技能。
