# 自动分解 GM 白名单设计

状态：设计已确认，等待书面规格复核后进入实施计划。

## 背景

当前自动分解每秒扫描已开启个人开关的在线玩家，仅处理宠物包。候选物品由现有 `CanFragment`、物品标记、金币和人物包空间规则决定。由于任何后来加入且符合底层规则的高级装备都会自动成为候选，存在误分解风险。

实际运行脚本树为 `D:\Debug\4月18日更新\Server\Scripts`。本设计只约束自动分解，不改变手动 NPC 分解。

## 目标

- 只有 GM 明确列入白名单的物品种类才允许自动分解。
- 初始白名单一次性复制当前物品数据库中符合原始系统分解规则的物品，保证切换当日的默认行为不突变。
- 初始名单生成后冻结；未来新增装备默认不能自动分解。
- GM 可以直接编辑配置文件，以一行一件的方式添加或删除物品。
- 白名单只增加一道准入条件，不能绕过现有安全检查。
- 配置加载失败时自动分解必须关闭准入，不能回退到旧的全量扫描。

## 非目标

- 不增加游戏内 GM 管理菜单或聊天命令。
- 不修改客户端、数据库结构、服务端 C# 分解公式、定时任务或玩家个人开关。
- 不增加按等级、稀有度或类型自动放行的通配规则。
- 不改变手动 NPC 分解行为。

## 方案选择

采用独立 Python 配置文件，以 `ItemInfo.Index` 为唯一判断键。物品名称和属性只用于 GM 阅读、搜索和复核。

未采用物品名称作为判断键，因为重名或改名可能造成误判。未采用数据库字段，因为需要同时修改数据库、服务端源码和管理工具，超出本需求的最小范围。

## 配置文件

新增运行配置：

`D:\Debug\4月18日更新\Server\Scripts\Npc\其他\自动分解配置.py`

格式为 Python 字典，按稀有度分组，每行一个物品：

```python
# -*- coding: utf-8 -*-

# 只有此表中的 ItemInfo.Index 才能自动分解。
# 删除整行表示禁止；复制一行并修改 Index 和名称表示允许。
# 修改后必须完整重载服务器脚本或重启服务端。

AUTO_FRAGMENT_ALLOWLIST = {
    # Common
    123: u"炼狱",        # Weapon | RequiredAmount=26

    # Superior
    456: u"示例高级装备", # Armour | RequiredAmount=40

    # Elite
    789: u"示例稀世装备", # Ring | RequiredAmount=0
}
```

维护规则：

- 冒号左侧的整数 Index 是唯一生效值。
- 名称和行尾属性用于人工核对，不参与运行判断。
- 每行保留结尾逗号，降低增删行时的语法错误风险。
- 不允许名称、等级区间、稀有度或类型通配。
- 空字典表示禁止所有自动分解。
- Index 重复不会放行额外物品，但生成和测试阶段必须检查并拒绝重复记录。

## 初始白名单生成

实施时只生成一次静态快照，数据源必须是当前服务端实际使用的物品数据库，而不是历史源码副本。

纳入条件与当前 `CanFragment` 的物品信息规则一致：

- `ItemType` 属于 `Weapon`、`Armour`、`Helmet`、`Necklace`、`Bracelet`、`Ring`、`Shoes`。
- `Rarity.Common` 的 `RequiredAmount` 必须大于 15。
- `Rarity.Superior` 和 `Rarity.Elite` 纳入。

实例级标记不参与静态名单生成；锁定、婚戒、不可精炼和无价值等标记仍在每次实际扫描时检查。

生成结果按 `Rarity`、`ItemType`、`Index` 排序，并在每行附带名称、类型和 `RequiredAmount`，方便 GM 搜索和删除高级装备。生成后不在服务器启动或脚本重载时自动重建。

## 运行流程

自动分解候选必须同时满足以下条件：

1. 玩家个人自动分解开关已开启。
2. 物品位于宠物包且对象、物品信息和数量有效。
3. 未命中现有锁定、婚戒、不可精炼、无价值保护。
4. `int(item.Info.Index)` 存在于 `AUTO_FRAGMENT_ALLOWLIST`。
5. 现有 `item.CanFragment()` 返回真。
6. 当前金币足够支付该件装备的分解成本。
7. 人物包可以容纳本轮产生的碎片。

白名单检查仅决定“是否允许进入现有候选流程”。成本、碎片类型、碎片数量、堆叠物品每周期只处理一件、扣费顺序和消息提示全部保持不变。

## 加载失败与安全行为

`便捷传送.py` 在加载白名单时捕获导入或语法异常：

- 将运行时白名单设为空字典。
- 在模块加载阶段记录一次明确错误日志。
- 不在每秒扫描中重复输出错误日志。
- 不影响便捷传送脚本的其他菜单功能。

任何白名单错误都必须“全部拒绝自动分解”，不得回退到只依赖 `CanFragment` 的旧行为。

## GM 操作流程

允许某件装备自动分解：

1. 从当前物品数据库确认该装备的 `ItemInfo.Index` 和名称。
2. 在对应稀有度分组中新增一行。
3. 完整重载服务器脚本或重启服务端。
4. 使用一次性测试装备确认生效。

禁止某件装备自动分解：

1. 按名称或 Index 搜索配置文件。
2. 删除对应整行。
3. 完整重载服务器脚本或重启服务端。
4. 使用一次性测试装备确认其保留在宠物包。

GM 编辑前应保留配置文件备份。脚本重载前的白名单继续生效，文件保存本身不承诺即时更新运行状态。

## 改动范围

运行文件：

- 新增 `Npc\其他\自动分解配置.py`。
- 仅在 `Npc\其他\便捷传送.py` 的自动分解入口增加安全导入和 Index 白名单判断。

验证文件：

- 扩展现有自动分解契约测试。
- 扩展现有宠物分解烟雾测试。
- 如需生成初始名单，生成工具仅作为一次性验证工具，不进入服务器周期调用路径。

## 验证标准

- 当前数据库中所有符合原始规则的物品都出现在初始白名单，且无重复 Index。
- 白名单内合法装备保持原有自动分解结果。
- 不在白名单内的 Common、Superior、Elite 装备均保持在宠物包中。
- 未来新增、但未加入白名单的装备不会自动分解。
- 白名单内的锁定、婚戒、不可精炼、无价值装备仍不会分解。
- 绑定和任务标记装备保持当前规则，仅在其 Index 已列入白名单时允许自动分解。
- 堆叠、金币不足、人物包空间不足的行为与当前实现一致。
- 空白名单、缺失配置和配置语法错误都不会消耗装备或金币。
- 运行脚本通过 IronPython 2.7 语法检查；契约和烟雾测试全部通过。
- 静态和烟雾测试不等同于在线验收；脚本完整重载后还需使用一次性测试装备验证允许项和禁止项各一件。

## 上线与回退

上线前先生成完整初始白名单，由 GM 删除明确需要保护的高级装备，再完整重载脚本。若未经 GM 审阅便直接使用完整初始名单，当前已符合旧规则的高级装备仍可能被自动分解。

回退时恢复 `便捷传送.py` 的原文件并移除白名单导入；配置文件可以保留备用。回退会恢复旧的全量自动分解候选行为，因此必须明确执行，不能由加载失败自动触发。
